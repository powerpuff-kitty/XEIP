## Release decision and next priorities

**No-go for production.** Cloudflare-native hosting remains an exploration; the separately approved private smoke is deployed and passed, but no organizational workflow or workload acceptance run exists. Keep self-hosted Keycloak as selected. The verified local implementation is a prototype, and passing correctness tests does not establish the operating targets.

The working local workflow is: signed agent request → Keycloak/device identity checks → session/tool policy → exact-content human approval → durable execution claim → MCP call → retained outcome and audit history. Current capabilities and their boundaries are:

| --- | --- | --- |

| Approval workflow | Keycloak authentication, explicit identity bindings, session/tool policy and a browser approval console | Local synthetic-provider/browser evidence does not establish your real users, network or operator workflow |

| Protocol and messaging | TypeScript SDK, Rust reference protocol/identity implementations, local relay admission, replay checks, resumable delivery and receipts | Relay remains loopback-only; broad federation and independent-client adoption are not established |

Safe activation, recovery of later acknowledgements, sustainable retention and hosted acceptance remain incomplete |

This is a reproduced recovery-boundary defect, not a signature bypass or a replay of a consumed claim. ## Identity and extension migration

The current `xeip.local-signed-envelopes/0.1` proves possession of the key whose URN equals `sender` and excludes extensions from signed bytes. Preserve those rules for existing clients. Do not add an optional bypass flag that lets callers claim arbitrary senders.

The experimental [0.2 successor](spec/entity-signed-envelopes.md) now implements the signing and local checkpoint portions of this contract:

1. Declare an explicit new carrier/profile version and domain-separated signing input.
2. Verify cryptographic integrity independently of authorization, then resolve the stable entity through a pinned, validated key-document chain.
3. Authorize only current root/device keys for that exact entity; enforce bounded retirement, status freshness and revocation at use time.
4. Bind the signature to routing fields, payload and application extensions, excluding only the signature carrier. Specify canonicalization and reject unknown critical extensions.
5. Persist highest accepted key generations and status serials across restart; define enrollment, rotation, recovery, trust-anchor change and emergency revocation operations.
6. Ship identical positive/negative JS, TS and Rust vectors: endorsed device as parent accepted; unrelated entity, removed device, expired status, rollback, edited extension and downgrade rejected.
7. Require explicit profile selection; no verification failure may fall back to self-certifying or unsigned operation.

The reference implementation and shared JS/TS/Rust vectors are recorded in [ADR 0011](spec/decisions/0011-entity-signed-envelopes.md) and the [implementation plan](spec/plans/entity-signed-envelopes.md). Base envelope 0.1 and legacy signing remain unchanged. The owner can now atomically update verified provisioning through the [live trust API](spec/live-entity-trust.md); bound revoked devices lose send/receive access and active streams close. Automated status distribution, certified trust recovery, external cryptographic review and production certification remain open. Stateless client verification does not itself persist trust history.

## Storage and performance decision

Evaluate the segmented prototype against an established backend (for example a transactional embedded store or an organization-operated durable message broker) using the same failure and load harness. Select based on the operator's workload and recovery objectives, not dependency count. Keep persistence behind a small acceptance/resume/receipt contract.

For the separate organization action ledger, [ADR 0014](spec/decisions/0014-organization-action-ledger.md) selects PostgreSQL's transactional state/audit boundary. Local tests cover concurrent claims, a lost commit response, abrupt database restart and logical backup restoration. This does not certify the prototype transport log or replace the combined workload/recovery evaluation. Approval consent is a short-lived grant: disabling an approver's provider login alone does not revoke prior consent; action, membership or key revocation does.

The audit machine measured ~16 synchronous fsync-always appends/second and ~2,700 batch appends/second. Batch acknowledgment has a loss window; loss of both an unsynced counter and record can also reuse a lost cursor. It is not equivalent to a stable-storage acknowledgment. Synchronous disk access also blocks the relay event loop. A production design must specify what success means, make ambiguous outcomes visible, and isolate/block-bound storage work appropriately. End-to-end exactly-once command effects require application-level idempotency; transport receipts cannot provide it.

## Product and market acceptance

Start with a human-approved agent action on an organization's service or device. Add only adapters required for that complete workflow. Capture discovery, identity, policy decision, approval, action, result, disconnect/recovery and audit inspection.

Recruit design partners and compare time to integrate, number of custom components, failure recovery and operational effort against direct MCP/A2A integration and an existing gateway. Acceptance requires evidence that XEIP reduces a real cost. A new general-purpose protocol, Rust implementation or vendor-neutral label is not sufficient differentiation.
