# Identity key-ID encoding plan and record

Scope: implement the encoding layer of the proposed identity profile in
[../identity.md](../identity.md) §2 as concrete, dependency-free Node ESM. This
slice produces the self-certifying key-id and the `urn:xeip:entity:` /
`urn:xeip:device:` strings from raw Ed25519 public key bytes. It adds **no**
signing, verification, key generation, curve validation or dependencies. It
agrees with ADR [0004](../decisions/0004-verifiable-identity.md) and the
dependency policy in ADR [0007](../decisions/0007-crypto-dependencies.md).

## Exact byte layout

```
key-id           = "z" || base58btc( multicodec || raw-public-key )
multicodec       = 0xed 0x01            (uint16 0xed01, unsigned LEB128 varint)
raw-public-key   = 32 bytes             (RFC 8032 §5.1.3 Ed25519 public key)
entity-id        = "urn:xeip:entity:" || key-id
device-id        = "urn:xeip:device:" || key-id
```

So the bytes fed to base58btc are always `[0xed, 0x01, b0, … , b31]` — 34 bytes
— and the resulting string is a multibase string whose first character `z`
declares base58btc. Example (RFC 8032 test vector 1 public key):

```
d75a980182b10ab7d54bfed3c964073a0ee172f3daa62325af021a68f707511a
  -> z6MktwupdmLXVVqTzCw4i46r4uGyosGXRnR3XjN4Zq7oMMsw
```

## Codec and multibase choice, and why

- **multicodec, not multihash.** The two-byte prefix names the key type
  (`ed25519-pub = 0xed01`); it is not a hash of the key. identity.md §2 calls
  the multihash reading out explicitly. `0xed01` is encoded as the varint
  `[0xed, 0x01]`.
- **base58btc (`z`), not base64url.** base58btc matches the W3C `did:key`
  convention (`z6Mk…`), so identifiers interoperate with that ecosystem and are
  visually compact, while avoiding the ambiguous glyphs `0 O I l`. base58btc is
  case-sensitive; the exact Bitcoin alphabet is fixed here rather than claiming
  "lowercase". base64url remains an allowed *input* spelling for key bytes, but
  the canonical identifier is always base58btc.
- **Hand-written base58btc is acceptable.** It is a well-defined base
  conversion with test vectors, not a cryptographic primitive, so it does not
  violate the "no custom crypto" rule in [../security.md](../security.md) and
  ADR 0007. It is implemented with a small, commented big-integer conversion
  that preserves leading-zero bytes as leading `1` characters.

## Anchor: how the genesis key document keeps the entity ID stable

`encodeKeyId` is pure: the same key bytes always yield the same key-id. The
entity ID is defined as `urn:xeip:entity:<key-id(genesis key)>`, i.e. the key-id
of the key in the entity's **first signed key document**, not the current root
key. Because the ID is derived from the fixed genesis key bytes, rotating the
root key (identity.md §6) produces a new signed key document but leaves the
entity ID unchanged; devices derive IDs from their own current keys and
therefore change on device rotation, which is acceptable since the entity, not
the device, is the stable principal. This module only computes the key-id; the
genesis-document lookup, signature check and generation chain are later work.

## Encoding boundary (what is deliberately out of scope)

Encoding now; cryptography later, behind the audited libraries selected in
ADR 0007.

- **In scope now:** byte layout, the multicodec prefix, base58btc, the `z`
  multibase prefix, the two URN forms, exact 32-byte length checking, and
  deterministic conformance vectors.
- **Out of scope (requires audited libraries per ADR 0007):** key generation;
  Ed25519 signing/verification (WebCrypto `crypto.subtle` / `ed25519-dalek`);
  canonical-curve-point, non-canonical-encoding and small-order point rejection
  (RFC 8032 §5.1.3); JWS/JWK/JCS; and any parsing of the signed key document.
- **Fail closed:** the encoding layer rejects any key that is not exactly 32
  bytes. It does **not** claim a key is a valid curve point; a verifier must run
  point validation before treating a recomputed key-id as authentic, exactly as
  identity.md §2 requires.

## Conformance-vector format

A JSON array of objects, one per key, generated by the encoder in
`tools/derive-keyid.mjs` and **reserved for future Rust and TypeScript
consumers** (no language but the JS encoder reads them yet):

```json
{ "name": "…", "publicKeyHex": "…64 hex…", "keyId": "z…",
  "entityUrn": "urn:xeip:entity:z…", "deviceUrn": "urn:xeip:device:z…" }
```

Negative entries omit `publicKeyHex`/URNs and instead carry
`{ "name": "…", "valid": false, "reason": "…", "keyId": "z…" }`; a decoder must
reject them.

The committed vectors (`conformance/fixtures/identity-keyid/…`) include an
all-zero key, an all-`0xff` key, two deterministic patterns, the RFC 8032 test
vector 1 public key, the W3C `did:key` `z6MkhaXg…` reference key, and negative
cases (missing multibase prefix, wrong payload length, invalid base58btc
character, wrong multicodec prefix). `npm run validate:fixtures` now checks them
with the JS encoder/decoder so a Rust or TypeScript implementation can prove
byte-for-byte agreement with this encoder and with the wider `did:key` ecosystem.
