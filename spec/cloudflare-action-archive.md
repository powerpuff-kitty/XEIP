# Verifiable action snapshots and archives

Purpose: preserve exact action payloads, approvals, consumed claims, outcomes/results and transition audit at a consistent historical cut, as a prerequisite for independent recovery and replay-safe retention. No deletion, restore or zero-loss acknowledgment guarantee is delivered by a periodic snapshot. Existing 500-user/200-agent/120-action-per-minute, P95 ≤2s, restore ≤1h and no-acknowledged-action-loss targets remain unchanged.

## Snapshot boundary

One organization ledger. `actionSnapshot` on the existing private owner binding captures the current maximum action-audit sequence, or an explicit earlier cut for previous-archive continuity. Cut 0 represents empty history; a nonzero cut must exist. The descriptor is exact `{schema:'xeip.action-snapshot/1',organization,cut,actions,digest}`. Read all current action/history consistency first. Within one synchronous read view, scan proposals at/before cut in increasing audit sequence and hash each reconstructed record. Hash domain `XEIP action snapshot v1\n`, canonical descriptor header without digest plus newline, then canonical records plus newline. Count<=10000. No checkpoint persistence, schema migration or owner audit mutation.

A record is exact `{row,history}` using versioned SQL row field names; canonical action, approver and result strings are preserved byte-for-byte. History includes only that action's events at/before cut. Derive state/version from that history; omit later approval/claim/result fields by setting them null until the corresponding transition is included. Reuse row/history validation. This works because action payloads are immutable, grant/claim/result fields are assigned only once by the verified schema, and audit rows cannot change. A cut is action evidence, not historical policy/trust configuration.

`actionPage` with exact cut and after-proposal-sequence returns `{cut,after,next,record}`. One record per page; null means no later proposal at/before cut. Cursor 0 starts; other cursors must name a proposal at/before cut. No offset pagination or caller-controlled identifiers/files. Validate current row/history before projecting its past state. Do not advance the cut or include later actions. Source rollback below the cut fails; a changed history between pages fails final snapshot digest verification. All routines are synchronous until the response, so ordinary writes cannot interleave within one capture/page read. No long-lived export lock.

## Private transport and bounds

Only existing privileged owner/namespace holders may invoke snapshot/page operations; default/public HTTP and RPC remain closed. Read-only export is not owner administration mutation. Owner receipt metadata stays correlated. Existing operations retain 64 KiB receipt limits; only actionPage allows 512 KiB, with page payload ≤480 KiB. This covers escaped canonical strings for the existing action 69,632, grant 4,096, result 131,072 and at most 4 audit actors of 4,096-byte bounds. Strict exact schemas/cursors/counts/digests, canonical JSON, bounded decoding and fixed redacted errors apply. No action payload or result in Worker logs. Operator collection prints only descriptor/count/checksum metadata. Raw owner inspection is privileged and can expose exported data; do not grant its broader credential to read-only third parties.

## Durable operator archive

Use one existing isolated OWNER session. Capture descriptor, collect exactly its action count plus an empty terminal page, validate every record and recompute the initial digest. Fixed numbered files with 0600 permissions in a new 0700 directory, exclusive creation and content/directory fsync precede a last-written canonical seal and successful output. Preserve failed partial directories; never overwrite, repair or delete source/prior archives. Reuse proven bounded filesystem helpers. Each read RPC deadline 30 seconds with no retry; late replies cannot seal an archive.

Manifest exact schema `xeip.action-archive/1`, public source config, snapshot descriptor, page count, aggregate file checksum, optional prior witness and manifest checksum. Zero-action archive has no record files. Verify offline with bounded pages, exact filenames/canonical bytes (including BOM rejection), row/history checks, ordered unique proposals/action keys, snapshot digest and exact file aggregate. Hashes are corruption detection; independently retain a trusted seal checksum. The filesystem and operator account are trusted, not a hostile-same-user sandbox.

With a prior complete verified archive, require identical public source config and organization. Ask the source to capture the prior cut and require the prior descriptor digest/count exactly; the new cut must not go backward. Record prior cut/digest/manifest checksum. A periodic snapshot still has a gap after its cut; authenticated source/account attribution, independent storage/custody and synchronous recovery fencing remain separate acceptance requirements.

## Capacity, privacy and compatibility

Archives contain sensitive tool arguments/results and principal metadata. They are private operator artifacts, not redacted reports; protected storage and approved retention are required. Do not copy separate runtime provider secrets/bearers or historic trust roots; sensitive values embedded in exact action arguments/results remain in the protected archive. No destructive retention default is inferred while policy and failure-boundary questions remain pending.

A full capture scans the retained ledger and hashes payloads; complete collection adds one request per action and copies all retained history. Bound memory via 128-key pages and one record at a time. Maximum-size CPU, database reads, filesystem duration and expense are not certified. Capture is synchronous and can delay other object requests; quantify hosted head-of-line latency before acceptance. Versioned export contracts require deliberate compatibility handling if ledger schema changes. Keep the existing Linux runtime and all interfaces unchanged.
