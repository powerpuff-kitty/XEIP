# Historical trust checkpoints

Status: local capture and validation verified; a dependency of complete control-state recovery, not a recovery guarantee.

The `xeip.trust-checkpoint/1` object binds `organization`, `configuration`, resolved `provisioning`, `revision`, `acceptedAt`, all retained `records`, and the original durable trust `checksum`. It includes signed key/status documents, including their signatures. Removed entities retain their rollback records. Physical SQLite chunk descriptors are resolved before capture; they can later be regenerated deterministically from canonical provisioning.

Validation requires the expected organization, exact field sets, bounded JSON, valid configuration, valid signatures at the original acceptance time, exact active-entity checkpoint agreement and the original state checksum. Bounds remain 8 MiB provisioning, 64 KiB configuration, 4,096 retained records and a 16 MiB checkpoint. Validation yields an isolated, deeply immutable object; it does not authorize current identities or extend status freshness. Hashes detect corruption, not a malicious replacement or consistent rollback: the eventual independent journal/witness must authenticate the selected history.

Within one runtime, the validator privately associates each immutable output with its canonical text. Revalidating that exact output for the same organization can reuse it and its encoding. Copies, wire-decoded values and externally frozen objects receive full validation; they cannot supply this private provenance. Weak keys do not keep discarded checkpoints alive, but each live validated checkpoint retains its canonical text. This optimization does not cache persisted storage reads or change checkpoint bytes, signature/time checks or size limits.

Expected-organization equality is a scope check, not authenticated provenance. The retained source checksum excludes organization and schema; the future journal must integrity-bind the organization and complete checkpoint bytes. Relabeling or wholesale replacement by an attacker is outside this codec's guarantee.

Capture reads ready durable trust synchronously, verifies schema and persisted row/chunk/record integrity against the instance's accepted checksum, then runs the complete historical validator at the original acceptance time. It also compares canonical validated provisioning to the literal resolved stored bytes. Live open/update paths retain their separate live preparation; capture avoids preparing the same signed data twice within one read. Coordinated organization capture still performs both pre- and post-synchronization reads. Updating, failed or closed instances refuse capture. It adds no public/owner RPC, persistence mutation or network operation. A caller must not treat this local capture as an independent durable receipt.

Full recovery still needs authority revisions/history, immutable lifecycle intent, administrative attempts/results, a consistent action/control cut, control acknowledgements gated by durable journal receipts, and external execution fencing. Existing action-only journal/restore formats remain unchanged. A trust checkpoint alone cannot initialize or activate a restored organization. Secrets, Keycloak and real MCP effects require separate operator custody and reconciliation.

Verification: native SQLite capture of inline/chunked/removed-entity state; refusal during pending synchronization and after corruption; offline validation of scope, signatures, hashes, metadata and retained records; existing trust/Cloudflare regression and strict types. No hosted SLO claim follows.
