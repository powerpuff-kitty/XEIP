# Fenced action database reconstruction

The accepted objective includes complete restore within one hour, no loss of acknowledged actions and no repeated effects. The recovery bundle now proves complete journal content and action history; it does not reconstruct a database. Implement actual SQLite reconstruction as the next dependency, while keeping the candidate durably unavailable until the still-required trust/authority/admin recovery and external execution fence are complete. This does not replace those requirements with action-only recovery or select a hosted failure boundary.

## Chosen approach

Initialize a separate, empty database with normal schema8 and a permanent staged-restore row in one transaction. Replay validated historical data transitions through existing action/audit SQL constraints, atomically advancing staged progress with each record. Do not drop triggers, replace source rows, replay tools or make a restored service active. Direct SQL dump replacement would bypass invariants; live-source repair before complete authority recovery could revive old consent. A fenced isolated candidate allows actual recoverability to be tested without that unsafe shortcut.

`StagedActionRestore.initialize(storage, manifest, {timeoutMs?})` requires no existing XEIP state; reject unrelated user tables as well, allowing only platform/internal SQLite storage. Validate/copy the exact archive manifest before mutation. Atomically create the ledger, insert immutable action recovery enrollment and initialize a restore intent binding the entire manifest. First sync precedes success. `open` requires existing matching intent, validates the full reconstructed prefix and synchronizes; it never initializes or repairs. Same intent may resume after an interrupted operation on a fresh instance. Wrong intent cannot adopt previous state.

`apply({entry,chunks})` validates the existing complete action record codec, journal scope/sequence/UUID/hash/base64 and exact prior action projection. New action records begin at a proposal; later records follow current history by exactly one event. Insert/update rows and append the exact global audit event, retain action counts and unique claim IDs, and advance progress in the same synchronous transaction. After synchronization, verify the committed record/progress before returning a blocked receipt. Exact current-tail retry revalidates and synchronizes; older/mismatched records never overwrite evidence. One in-flight operation; uncertain storage/deadline outcomes quarantine and require a fresh open. A late sync or close cannot reactivate the instance.

`verify()` fully reconciles the actual restored rows/audit against the manifest, reconstructs every deterministic journal record, checks the full chain, raw byte totals, exact files checksum and previous witness, and only then persists phase `verified` and synchronizes. That phase is still fenced. Receipts identify manifest/progress/counts and `blocked:true`, never credentials, arguments, results or an execution capability. No activation, reset, deletion or namespace selection API exists.

## Schema and runtime gate

Schema8 adds singleton `xeip_action_restore` with immutable canonical manifest intent, contiguous sequence/checksum/byte progress, phase `restoring|verified`, and a checked row checksum. SQL triggers reject replacement/deletion, changed intent, noncontiguous progress, phase reversal and updates after verified. Existing migration1..7 bytes/checksums remain unchanged. Old executables reject schema8. Normal initializeLedger and verifyLedgerSchema reject any restore row, independently of its contents or phase. A structural-only verifier is available solely to the restore implementation; it cannot make normal data/service operations ignore the fence.

The restore implementation cannot target an already initialized organization, even an empty unconfigured ledger. The organization service already rejects a database without its normal lifecycle intent; the explicit schema fence also blocks direct ledger/trust/authority/journal activation. No production Worker restore entrypoint is introduced before the complete recovery operating model exists. Native private conformance controls exercise the module, not a public repair route.

## Reconciliation and bounds

The source remains capped at10,000 actions and40,000 historical transitions. Process bounded records rather than buffer the complete archive. Rebuild full journal/files hashes from each actual historical projection on open/verify; detect orphan/gapped audit, altered historical actors/results/claims, missing/extra actions, counts, changed binding or intent, and schema drift. Keep control-plane tables empty. Pin URL and full manifest as evidence, but do not contact or claim freshness of the hosted journal. New commits after the bundle cut require later coordinated reconciliation and external fencing before any activation.

Extract platform-neutral archive/action record codecs so the offline verifier and native reconstruction share exact format validation and UUID preparation. Node filesystem tools remain outside Worker imports. This refactor must preserve journal byte/ID compatibility. Synchronization deadlines100..10000ms, default10000, use a timer/elapsed checkpoint appropriate to workerd; admission is instance-local, and timeout permanently quarantines that instance so it cannot report late success. A fresh open may reconcile and synchronize the same storage while an earlier sync promise remains pending; the abandoned operation has no remaining mutation continuation. Full-history reconstruction cost remains an explicit hosted timing gate.

## Tests and remaining requirements

Native SQLite cases: empty and multi-state reconstruction with rows/audit identical to original evidence; unfinished/succeeded/failed/indeterminate claims remain consumed; normal initialize/store/service cannot activate restoring or verified candidates; restart/resume, exact-tail retry, stale/forked data, missing intent/binding, corruption, atomic fault rollback, sync uncertainty/timeout/close, SQL replacement guards; schema7 migration preserves records/checksums, rollback after DDL mutation and old executable refusal. Real signed Worker→journal→bundle→isolated candidate integration must preserve one effect and leave the candidate blocked.

One scoped review and fix pass, full macOS/Linux suites/types, exact Worker/scheduler artifacts and refreshed Linux image when root manifests change. Full source recovery, control-plane capture/restoration, coordinated hosted journal/execution fence, retention, private routing, capacity/latency/recovery and security/operator/pilot acceptance remain required. No deployment, real credentials/data or resources are authorized by this local increment.
