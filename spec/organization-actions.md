# Organization action approval contract

Implementation scope: the first internal MCP workflow, following [Keycloak authentication](organization-auth.md). This experimental ledger is integrated into the [signed organization service](organization-service.md); a production deployment is not yet certified.

## Authorization and exact approval

An authenticated principal must also pass current entity trust and explicit operator-provisioned session membership. The policy permits only configured target IDs and tool names; a request cannot supply a URL or credentials. Agents require the `agent` API role and session agent membership. Approvers require the `approver` API role and session approver membership. The requester cannot approve its own action, including through another subject mapped to the same entity. No wildcard memberships or tools. Roles alone grant nothing.

The policy is immutable per service instance. Its revision is a SHA-256 digest of the entire canonical configuration, including explicit target deployment revisions. Changing membership, allowed tools or a target revision invalidates outstanding approvals. Operator rollout must stop/drain the old writer before starting the new policy; distributed hot reload is outside this first profile.

The request is exactly `{id, session, target, tool, arguments, expiresAt}`. IDs are bounded ASCII identifiers, arguments a bounded JSON object, and expiry is a whole Unix second in the future and at most five minutes away. Canonical action content binds protocol version, request ID, session, requester subject/entity/key, target ID/revision/recipient, tool, every argument, expiry and policy revision. The server computes a domain-separated SHA-256 digest. The human approves the displayed exact content and digest; an approval never covers later edits or a different session, target, key or policy revision. The approval API must accept the expected digest and perform a compare against the stored action.

At approval and execution, recheck current membership, role, identity trust, provider token status and expiry. A rejected or expired action cannot be resurrected. Revocation wins before an execution claim commits. Once execution begins, revocation cannot guarantee cancellation of an effect already sent upstream.

The approver's consent becomes a short-lived grant, capped by both action expiry and the approver token's expiry. Do not persist their bearer token. At execution, revalidate the executing agent's provider status and both actors' current entity trust and local membership. Disabling the approver's login does not itself withdraw an already-issued grant: explicitly revoke the action or its local membership/key. This distinction must be visible in the operator runbook and human approval UI. A future centralized grant-revocation feed may tighten it; offline assumptions must not claim immediate provider-driven cancellation of issued grants.

## Durable state and concurrency

Use PostgreSQL for the organization action ledger, separate from the local relay's segmented transport log. The initial schema needs actions, decisions/execution claims and append-only audit events. One transaction creates immutable action content and its audit event. A row lock serializes approval, revocation and execution claims; one transaction changes state and adds its audit event. A unique request ID plus digest comparison makes retries idempotent and conflicting reuse a conflict. Scope lookups by session and authorized actor before revealing content.

States are `pending`, `approved`, `rejected`, `revoked`, `executing`, `succeeded`, `failed` and `indeterminate`. A single durable claim changes `approved` to `executing` before any upstream call. Replays cannot acquire another claim. A process crash or ambiguous upstream timeout leaves an indeterminate effect; restart must never automatically re-execute it. Operators reconcile through upstream evidence. Exactly-once effects require upstream idempotency, not an XEIP receipt.

Require `fsync=on`, `full_page_writes=on` and synchronous commit for acknowledged database transactions. Return success only after commit; a lost commit response is ambiguous and must be resolved by request ID. Use one checked-out database client per transaction, bounded pool/query/lock deadlines and parameterized SQL. Migrations are versioned, checksummed and transactional; runtime credentials cannot alter schema or erase audit records. Backup/restore, corruption, storage exhaustion and process-kill drills remain G3 gates before a supported deployment.

`inspect(principal, session, id)` resolves stored state independently of action expiry or old policy revision, using current authenticated membership. It returns no execution claim capability. Exact `propose` retries still require current execution eligibility; use inspection after expiry or policy changes. Check local eligibility before acquiring action locks, then check again under the lock and after provider revalidation. Pool acquisition and client query timeouts must each be configured between 100 and 10000 ms. The store also limits server statement/lock waits and authorization callbacks; transport connection/pool limits remain necessary.

Action arguments and results may contain sensitive organization data. Store only what the workflow needs, keep bearer/client secrets out of rows and logs, and require operator-approved retention and encrypted storage/backup. Migration 002 adds a canonical result of at most 128 KiB to terminal succeeded/failed actions; indeterminate actions have no trustworthy result. Results are immutable, and repeating completion requires the exact same outcome and result. Current authorized members can inspect the historical result without receiving execution authority. Audit metadata records actor, session, action digest, transition and time; it must not duplicate argument or result contents. Retention must preserve audit linkage and never make a consumed ID reusable inside the supported replay window.

## Verification and remaining boundaries

Test deny-by-default policy, exact-content digests, schema/size bounds, caller/config mutation, different subject/same entity self-approval, expiry, revoked membership and policy change. Database tests use real PostgreSQL for simultaneous claims, commit failure/restart, migration checks and backup restoration. The signed HTTP/MCP integration preserves these checks after body reads and immediately before effects, including real Keycloak revocation after claiming. Human approval UI, operational reconciliation and deployment acceptance remain separate requirements.

Sources: PostgreSQL documents [row-level locking](https://www.postgresql.org/docs/current/explicit-locking.html); node-postgres requires [one client for each transaction](https://node-postgres.com/features/transactions). Supported versions follow the [PostgreSQL support policy](https://www.postgresql.org/support/versioning/).
