# Automatic Cloudflare trust refresh

Status: experimental implementation; no hosted deployment or publisher acceptance.

## Contract and boundaries

The accepted single-organization workload remains 500 users, 200 agents and 120 actions/minute, P95 machine operation <=2 seconds, restore <=1 hour and no loss of acknowledged actions. This increment removes manual polling as a prerequisite for fresh signed trust; it does not certify those targets.

An optional public `trustFeed: {url, timeoutMs?}` profile configures one exact, canonical HTTPS URL, without credentials, query or fragment. Timeout defaults to 5000ms, allowed 100..10000ms. Trust maximum age must be at least 180 seconds when enabled. The URL and timeout become immutable deployment intent; existing configurations without this field retain their exact intent. Enabling/changing the source for an initialized deployment requires a future explicit migration, never silent adoption. A separate `trustFeedToken` credential is required exactly when the feed exists, RFC6750 token characters, <=4096 bytes. It can rotate without changing intent. Neither credential nor signing keys enter durable state, artifacts, logs or responses.

When configured, the artifact includes a separate scheduler Worker with a `* * * * *` Cron Trigger and a private service binding to the organization Worker’s named `RefreshEntrypoint`, with `purpose: trust-refresh`. The main default entrypoint remains fetch-only and its cron list is always empty. The scheduler/default binding is privileged; it must never be granted to an ordinary client. Its handler calls the fixed private refresh capability, which selects the fixed object; no HTTP owner route or owner-supplied URL is accepted. The scheduler has no public routes and HTTP returns404. Default service bindings can invoke scheduled handlers by RPC on this platform, so handler shape/branding is not treated as a security boundary. Only one refresh runs per object instance; overlapping calls fail without fetching or mutating. Eviction loses only this admission state. A duplicate later poll is safe because it revalidates the latest durable revision and identical content produces no write. No tool execution, queue retry, automatic initialization or recovery from quarantined storage occurs.

The feed is a complete `{keyDocuments, statusDocuments}` JSON replacement. GET uses the pinned URL, bearer header, no redirects and no cache; accept only exact 200 and JSON UTF-8. Bound the entire response (headers and body) by the timeout; cap decoded body at 2,000,000 bytes to leave space for the existing 2MiB owner envelope; strict duplicate-free JSON, depth32 and 262144 nodes. Reject other status/media types, invalid UTF-8, unsupported content encoding, excessive declared/streamed length and stalled streams. Cancel failures and redact errors. No immediate retries.

The owner must explicitly initialize authority and provision a nonempty roster first. Before network I/O capture trust revision. After fetch require the same trust revision, initialized/usable state and no currently in-progress owner mutation. A completed authority-only update during the fetch is permitted: it does not change the trust roster and is not overwritten by refresh. Validate fresh signatures, current anchors, key chain history, monotonic checkpoints, exact active entity set, and existing anchors. The feed cannot add identities, remove identities, or restore omitted identities; owner provisioning changes the roster. A verified byte-canonical duplicate returns unchanged without extending status freshness or consuming audit records. Changed data goes through `manage(refreshTrust)` with a fresh UUID and fixed `automation:trust-feed` actor, preserving durable start-before-mutation and completion-before-acknowledgment. Storage uncertainty quarantines as before. Feed/network/signature failures preserve current trust, which continues to expire normally.

Redacted `xeip.trust-refresh` outcome logs distinguish disabled, not_ready, busy, unchanged, updated and failed. Failures reject the scheduled handler so platform invocation monitoring can report them. Logs are diagnostic; only admitted changed trust has durable audit records. Signing/publishing remains external and publisher outages can deny new work after expiry. Operators must monitor cron failures plus readiness and signed-document age, not just HTTP liveness.

## Threat model and residual risk

Assets: entity authority, single-use action claims, owner history and outbound feed token. Actors: public clients, feed publisher, deployment owner, namespace-binding holder, compromised/slow feed and storage failures. Public callers cannot invoke refresh; namespace holders remain privileged. HTTPS protects transport; independent signatures/checkpoints restrict publisher authority. A compromised publisher can withhold fresh status (availability loss), but cannot introduce an unprovisioned entity or roll back revocation. Credential exfiltration through redirects is forbidden. Races that change trust revision discard the fetched candidate; currently in-progress owner operations also exclude refresh. Neither local hashes nor cron provide independent recovery protection.

The feed must publish fresh complete data frequently enough to cover polling, network latency, signing and scheduling delay. A minute schedule and 180-second minimum age are guardrails, not an availability guarantee. The 100000-record owner journal remains finite: one changed refresh/minute alone consumes 2880 records/day. Retention/export, hosted scheduling/egress/IAM, signer custody and real 700-identity publisher integration remain production gates.
