# Experimental action recovery integration

When explicitly configured, the action store and organization service now wait for an independent recovery receipt before acknowledging an action transition or returning a tool-execution claim. The [Worker profile](WORKER.md#configure-action-recovery-before-initialization) can now opt into the authenticated HTTPS client before initialization; default profiles remain unconfigured. This is locally verified integration code, not deployed zero-loss protection or a complete restore system.

## Ordering and startup

Each proposal, approval/rejection, revocation, claim and completion already has an atomic source row/audit transaction. The integration synchronizes that transaction, publishes a deterministic `xeip.action-recovery/1` payload containing the exact historical action row and transition history, validates the journal receipt and head, and then performs the existing late authorization check. The normal executor still checks authorization immediately before sending a tool call. A recovery receipt is data-integrity evidence, not an execution capability.

Schema7 adds an immutable source enrollment record for the journal organization, UUID stream, capacity and genesis checksum. Enrollment requires an empty source and an explicitly initialized empty journal. The service also pins that public descriptor in its lifecycle intent. Removing the adapter, changing its identity/caps, deleting the binding, or pointing at an inconsistent history prevents activation. There is no disable/reset API. Existing unconfigured installations retain their experimental behavior; upgrading alone does not enroll them or give them a recovery guarantee. Existing populated sources need a separately reviewed enrollment/migration procedure.

Startup reconstructs all deterministic transition records and compares the committed journal chain. Equal histories activate. Exactly one unacknowledged local transition beyond the journal can be published before activation; this never executes a tool or returns an old claim. A journal ahead of the source, divergent payloads, missing sequences or multiple unpublished transitions fence the source. A lost append response is resolved by comparing persisted histories on fresh open. Consumed claims remain consumed, even when no tool call was ever sent.

Recovery-enabled operations serialize across authorization, local sync and remote confirmation. New public admission conflicts; inspection and archive operations cannot expose pending state. Final effect authorization for an already-issued claim and internal completion wait in a bounded FIFO of at most32 entries, using the journal timeout as the admission deadline. Ownership transfers before waking a waiter, so new requests cannot overtake it. Timeout/close removes waiting work without running it later; no external effect is retried. Deadline, storage, receipt and continuity failures quarantine the instance. Closing during an await cannot reactivate it. Internal completion still records an already-sent outcome after caller credentials expire, and waits for recovery durability before acknowledging it. Final effect authorization waits through ordinary busy periods and rechecks authority/recovery after admission, instead of treating unrelated traffic as revocation. Readiness remains false while admission is busy; hosted probe and load behavior still need acceptance.

## Adapter contract

`DurableActionStore.open(storage, authority, {organization, recovery})` and `OrganizationService.open(storage, configuration, recovery)` accept an injected adapter. The service controls initial enrollment during its explicit owner setup. Direct store enrollment additionally requires `recovery.initialize: true`.

`recovery.options` uses the [journal scope/capacity options](RECOVERY_JOURNAL.md); timeout is runtime-only. `recovery.client` supplies asynchronous `head()`, `entry(sequence)` and `append(request)` methods matching `RecoveryJournal`. The client must authenticate and pin the intended endpoint/identity, preserve exact bounded records, and return a receipt only after the journal's durability boundary. It must not automatically retry effects or create/reset a namespace. Secrets and executable adapter capabilities are never persisted in lifecycle intent.

The native conformance fixture uses distinct source/journal SQLite Durable Objects, with fault injection only in test modules. An experimental [authenticated HTTPS client and handler](RECOVERY_HTTP.md) now implement this adapter boundary, with native transport integration tests. The Worker now accepts explicit public recovery settings and a separate secret, with enrollment through its existing private owner initialization. There is no hosted journal or journal provisioning command. Enable a production adapter only when the failure boundary, transport/IAM and operating model have been accepted.

## Handling a fence

Preserve the source and journal evidence. Do not delete enrollment, recreate the namespace, truncate the journal, replay a claim or downgrade the schema to make readiness pass. A fresh open can resolve one interrupted append; history disagreement needs the forthcoming verified restore/reconciliation procedure. This integration detects source rollback against the journal but does not restore source rows.

A consistent rollback/loss of both databases still requires an independent witness or provider boundary. Hashes do not defend against a privileged complete database/adapter rewrite. The journal's `healthy()` check is not continuous validation of all historical payloads. Source startup compares full transition history; hosted durability and ongoing integrity monitoring remain operator requirements.

Retained action/journal caps and complete startup scans are finite prototype bounds. Repeated exact row/history capture increases storage and startup cost, and serialized admission may conflict under load. No throughput, two-second latency, one-hour restore, source trust/authority/admin recovery, retention or production pilot claim follows from local tests. Keycloak and private MCP hosting/connectivity remain unchanged.

Schema6 data and logical checksums are preserved by the additive migration. Old executables reject schema7; reverting code is not a supported database downgrade. See the [design](../../../spec/cloudflare-action-recovery.md), [verification and review ledger](../../../spec/plans/cloudflare-action-recovery.md), and run `npm run test:cloudflare` plus `npm run typecheck:cloudflare`.

The [recovery bundle collector](RECOVERY_ARCHIVE.md) now reads a fixed complete journal prefix into private durable files and verifies payloads, chained history and prior witnesses offline. Separate action interpretation checks exact transition continuity and consumed claims. It performs no restore or replay and does not certify independent hosting or zero-loss recovery.
