# Experimental organization service lifecycle

`OrganizationService` owns the signed request handler, persistent trust, authority, ledger and MCP connector for one live organization object. The [Worker package and operator runner](WORKER.md) provide experimental deployment entrypoints; hosted organizational acceptance remains required. Never expose its owner methods as public HTTP routes or deploy a conformance worker.

Create it once with `await OrganizationService.open(storage, configuration)`. Configuration contains organization, exact HTTPS origin, gateway entity, trust freshness settings, configured MCP targets and the runtime introspection secret. Target credentials remain runtime-only. The stored public configuration pins target endpoints, revision, recipient, resource, issuer, scope and client ID. A fresh instance may use rotated secrets, but changing public identity/routing fields fails closed. Such changes need an explicit migration workflow; do not delete the marker or use a new namespace to conceal existing acknowledged actions.

| Service state | Meaning and next action |
| --- | --- |
| `uninitialized` | Empty XEIP namespace, no schema written by public traffic. Owner must initialize. |
| `initializing` | Durable setup intent exists. Only an exact owner retry may finish it. Public actions/readiness remain unavailable. |
| `initialized` | Setup is complete. Readiness still requires nonempty fresh trust, usable ledger/authority and a successful provider probe. |
| `failed` | Integrity or persistence failure. Investigate; a fresh instance must verify stored state. No reset is provided. |
| `closed` | Instance disabled; pending setup cannot reactivate it. |

First call owner-only `initialize({authentication, policy})`, with the introspection secret omitted from authentication. The service validates it before writing, atomically creates schema and immutable intent, synchronizes that intent, creates empty trust and authority, then persists completion. Empty trust permits no action. Follow with `refreshTrust(provisioning, {expectedRevision: 0})` using complete signed key/status documents. Read the returned/current trust revision for subsequent refreshes. This separation lets interrupted setup resume without relying on a soon-expiring status bundle.

A repeated initialize must contain the original configuration, even after later policy changes. It cannot overwrite those changes or recreate missing completed trust/authority. An interrupted setup may resume only unchanged initial components; unexpected component revisions or data fail closed. The v4 migration preserves v1-v3 action, audit, trust and authority rows. Existing experimental data without a lifecycle marker is not silently adopted: a separate reviewed adoption procedure is required.

The internal `lifecycleCheckpoint()` method captures this original public setup intent and phase after storage synchronization and an exact recheck. It excludes credentials, refuses overlap with control mutations and can preserve interrupted initialization without completing it. This [historical checkpoint](../../../spec/cloudflare-lifecycle-checkpoint.md) is a recovery dependency, not a public/owner RPC or a restore activation mechanism. Credentials require separate custody, and complete recovery must also reconcile actions, trust, authority and administrative history.

For initialized organizations, internal `recoveryCheckpoint()` captures lifecycle, trust, authority and administrative checkpoints together with a fixed historical action cut. It holds the control-operation guard across synchronization and exact recheck, while allowing actions to finish. The manifest binds all components; `recoveryPage()` provides bounded action and control history reads. A missing action cut triggers ledger reconciliation before an ordinary conflict can be returned, so deleted history cannot bypass quarantine. The [complete bundle library](ORGANIZATION_BUNDLE.md) collects and verifies the pages bound by these [coordinated checkpoints](../../../spec/cloudflare-organization-checkpoint.md). Bounded operator transport, independent journal receipts and fenced restoration remain required. They expose no public route or owner command and do not authorize activation of restored state.

Internal `beginRecoveryExport(operator)`, `recoveryExportPart(operator, exportId, component, index)`, `recoveryExportPage(operator, exportId, options)` and `closeRecoveryExport(operator, exportId)` provide one ephemeral export session per service instance. The session is bound to the operator supplied by the trusted owner boundary; these methods are not authentication endpoints. Begin returns a manifest and component byte/hash/part descriptors. Parts contain at most256KiB decoded canonical data. Scoped history reads retain the captured cut after legitimate control updates. Successful reads renew a30-second idle deadline, bounded by a one-hour lifetime; overlapping reads conflict, expiry releases the session, and source close/failure prevents revival. Existing current-head `recoveryPage()` behavior is unchanged. The private owner commands and [collection CLI](ORGANIZATION_BUNDLE.md) are implemented in repository source; large-source resource measurements and hosted acceptance remain open. No public route or new cloud deployment exists.

`updateAuthority(configuration, {expectedRevision})` changes provider bindings and policy under the existing authority rules. Referenced policy targets must match configured target IDs/revisions/recipients and stay within their tool allowlists. Updates cannot change pinned issuer/audience/introspection-client identity. Owner mutations are exclusive, revisions reject stale writes, and in-flight action guards observe changes. Invalid input preserves usable state; storage/synchronization failures disable the service. The [private owner entrypoint](WORKER.md) now provides bounded commands and binding attribution with a durable journal. Opt-in [automatic refresh](REFRESH.md) preserves the owner-provisioned roster; real deployment IAM and signer/publisher operations still need acceptance.

`fetch(request, {waitUntil})` serves the same bounded `/live`, `/ready` and signed `/v1/actions` routes as the transport adapter. `/ready` probes only identity-provider availability and local authority/storage/trust health; it never calls an MCP tool. A revision change during the probe invalidates a late success. Missing or stale trust, provider outage and ledger quarantine report unready. Initialization state alone is not availability: local ledger quarantine may leave the lifecycle marked initialized while rejecting requests and pending effects. `/live` is only process liveness. Attach task completion to the Durable Object lifetime; cancellation cannot undo a remote effect already sent.

The service retains the durable claim → one tool call → durable outcome boundary. Final authorization checks service and ledger health before and after asynchronous authority checks, so detected ledger corruption during OAuth or authorization prevents the pending tool call. If the result commit is ambiguous, the caller receives failure; reopening preserves the recorded result or consumed claim and cannot replay the effect. Point-in-time restore and loss of all database replicas still require independent recovery fencing and acknowledgment reconciliation before execution resumes.

Verify with `npm run test:cloudflare` and `npm run typecheck:cloudflare`. Lifecycle tests use actual workerd/SQLite, RSA provider responses, signed identity documents and the independent official MCP SDK server. They inject bootstrap and outcome sync faults, restart the runtime, test expiry/revocation and compare migrated rows byte-for-byte. Literal-loopback allowances are fixture conveniences inherited from shared adapters; production packaging must reject them. Local tests do not establish hosted IAM, TLS/network routing, capacity, disaster recovery or human login acceptance.
