# Experimental recovery journal core

This module is **not deployed**. The [action recovery integration](ACTION_RECOVERY.md) can now use it through an explicitly injected adapter to gate action acknowledgements and execution claims. The organization Worker does not export the journal. Its optional [recovery profile](WORKER.md#configure-action-recovery-before-initialization) configures a client before initialization; default profiles still provide no recovery guarantee.

`RecoveryJournal.initialize(storage, options)` explicitly creates an isolated journal database. `open` requires the same organization, UUID stream and persisted capacity limits, validates the complete history and synchronizes before returning. Never use the source action database as its storage. There is no reset, migration, deletion or retention API.

`append` accepts an expected head, unique UUID, byte length, payload SHA256 and canonical base64 parts. It atomically stores a chained immutable header and all parts, synchronizes storage, revalidates and then returns a receipt. Payloads are opaque bytes; a receipt grants no action or execution authority. The action integration validates a versioned transition format and gates configured source acknowledgements/effects on the independent durable receipt. Other source state still requires its own recoverable format.

Concurrent writes conflict; reads cannot expose a pending unsynchronized head. Stale heads, historical repeated IDs and exhausted caps conflict without disabling the healthy journal. Only an exact current-tail retry with the same predecessor and payload is idempotent, and it still synchronizes before returning. Storage failures, timeouts and ambiguous commits quarantine the instance. Open a fresh instance and reconcile its head before deciding what happened; never automatically retry a tool effect.

`healthy()` reports that the instance is ready and that the schema/catalog and cached tail header still match storage. It is not a complete ongoing integrity attestation: historical payload corruption introduced after open can remain undetected until a selected read or fresh open validates it. Future source integration must not substitute this health check for reconciliation.

`head`, `entry(sequence)` and `part(sequence, index)` support reconstruction. Opening verifies the complete chain and every payload. Part reads validate the entire selected entry plus adjacent links before returning one part. Each part is at most 256 KiB decoded / 349,528 bytes encoded. Entries are capped at 16 MiB, retained raw data at 1 GiB and entries at 1,000,000; lower persisted caps are supported. Base64, headers and database indexes add storage overhead. These limits and full-history scans are prototype bounds, not evidence of sustainable rollout capacity. The public request limits have not been widened.

A live instance rejects an unexpected head change. A fresh instance cannot detect a consistent rollback of the **whole journal** without an independent witness: its hashes are integrity checks, not an external time source or authenticated backup. Local conformance demonstrates this limitation explicitly. Separate storage in the same provider/account cannot cover loss of that provider/account. The accepted failure boundary and independent hosting/IAM design remain undecided.

An experimental [authenticated HTTPS client and handler](RECOVERY_HTTP.md) now provide a provider-neutral transport boundary. They cannot initialize/reset the journal and are not deployed. The Worker profile now configures the source client; independent journal hosting remains open. Remaining work: coordinated durable action/control recovery, verified restore tooling, accepted independent hosting/enrollment/IAM and retention policy, hosted durability/fault testing, capacity/latency evidence, and security/operator acceptance. Configured action acknowledgement ordering and startup fencing now have local integration evidence. Keep Keycloak and the existing Linux deployment requirements until an operating-model change is accepted.

See the [contract](../../../spec/cloudflare-recovery-journal.md) and [implementation/review evidence](../../../spec/plans/cloudflare-recovery-journal.md). Run `npm run test:cloudflare` and `npm run typecheck:cloudflare`; the recovery fixture uses local real workerd/SQLite and synthetic data only.

The [recovery bundle collector](RECOVERY_ARCHIVE.md) now reads a fixed complete journal prefix into private durable files and verifies payloads, chained history and prior witnesses offline. Separate action interpretation checks exact transition continuity and consumed claims. It performs no restore or replay and does not certify independent hosting or zero-loss recovery.

## Source state still missing from complete recovery

The current typed source integration records action/audit transitions only. The following [schema](schema.mjs) state is not reconstructed by an action bundle:

A [historical trust checkpoint codec](../../../spec/cloudflare-trust-checkpoint.md) now captures resolved signed provisioning and retained rollback records from a ready source. It is a local capture/validation dependency only: it has no journal append, acknowledgement gate or restoration path. The missing state and complete-recovery requirements below remain open.

[Historical authority capture](../../../spec/cloudflare-authority-checkpoint.md) now preserves current public configuration and reads the complete revision chain through bounded pages pinned to one checkpoint. Its verifier requires genesis-to-head continuity; concurrent updates conflict. This is likewise a local dependency without durable source acknowledgement gating or restoration.

[Historical lifecycle capture](../../../spec/cloudflare-lifecycle-checkpoint.md) preserves exact initial setup intent, public runtime settings and the initializing/initialized phase. It synchronizes and rechecks storage under the control-operation guard, excludes credentials, and validates organization/target/recovery bindings. Capture does not complete interrupted setup or grant permission to activate restored state. Administrative history and a coordinated action/control cut still need independent journal receipt gating and complete fenced reconstruction.

[Historical administrative capture](../../../spec/cloudflare-admin-checkpoint.md) adds a fixed scoped journal head and bounded pages with complete-history verification. It preserves original attempt/result records and unresolved starts, rejects mixed heads and unmatched/duplicate results, and refuses capture during active mutations. These internal methods introduce no owner RPC or command replay.

[Coordinated organization capture](../../../spec/cloudflare-organization-checkpoint.md) now binds all four controls and a fixed action snapshot in one manifest. Synchronous capture and post-sync recheck under the control guard preserve one initialized source view while later actions can proceed. Bounded pages remain subject to complete-history verification; the manifest alone is not a complete bundle. Capture has no independent receipt, does not gate control acknowledgements and cannot activate restoration. The current action journal's sequence equals action audit sequence: inserting control records into that stream would break existing reconciliation. The [organization bundle library](ORGANIZATION_BUNDLE.md) now collects and verifies the complete cut locally. The [organization restore library](ORGANIZATION_RESTORE.md) now reconstructs the complete bundle into a permanently fenced candidate. Bounded operator transport, a coordinated durability protocol, current-journal reconciliation and external execution fencing remain required.

| State                                                             | Required preserved meaning                                                                                                          |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `xeip_trust_state`, `xeip_trust_chunks`, `xeip_trust_checkpoints` | Complete signed provisioning content and retained anti-rollback/removed-entity checkpoints, not merely the current trust digest     |
| `xeip_authority_state`, `xeip_authority_events`                   | Exact authority configuration, revision and complete event continuity                                                               |
| `xeip_service_state`                                              | Initialized lifecycle intent and its pinned public configuration/recovery enrollment; secrets remain separately provisioned         |
| `xeip_owner_events`                                               | Full administrative attempt/result history, including unresolved attempts; event digests cannot reconstruct omitted command content |

`StagedActionRestore` explicitly requires these control-plane tables to remain empty and normal runtime verification rejects its permanent fence. Successful action reconstruction therefore cannot be promoted by supplying a profile or copying current trust metadata. Complete recovery still needs typed control-plane capture before acknowledgement, a consistent restored cut across action and control state, current-journal reconciliation and external execution fencing. Keycloak state, secret custody and actual MCP-side effects also require the accepted operator recovery procedure; they are not contained in the SQLite action bundle.
